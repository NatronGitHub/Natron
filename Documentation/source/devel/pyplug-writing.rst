.. _pyplugWriting:

Writing a PyPlug
================

A *PyPlug* is a Python script that re-creates the content of a Group node. Natron registers it as
a plug-in of its own: it appears in the node menus and the tab menu of the node graph, and
:func:`app.createNode()<NatronEngine.App.createNode>` can create it from its plug-in ID. When the
user creates the node, Natron creates a Group node and calls the script to fill it.

The easiest way to make a PyPlug is to build the Group in the user interface and export it
(see :ref:`groups`). This page explains what the exported script contains, how to write one by
hand, and how to distribute it.

.. _pyplugWriting-path:

The steps, from a first PyPlug to its distribution:

1. **A first PyPlug.** Build a Group and export it (:ref:`groups-export`), or write the file by
   hand (:ref:`pyplugWriting-createInstance`). Either way, the file must follow the rules of
   :ref:`pyplugWriting-file`.
2. **Parameters.** Give the group its own parameters and drive the nodes inside with
   expressions or links (:ref:`pyplugWriting-params`).
3. **Callbacks.** React to the user, e.g. to a button, in the ``Ext.py`` file
   (:ref:`pyplugWriting-ext`, and :ref:`callbacks` for every callback).
4. **IDs, versions and updates.** Choose the plug-in ID and version
   (:ref:`pyplugWriting-versions`), and edit an installed PyPlug and export it again
   (:ref:`pyplugWriting-update`). A script that adds nodes to the graph instead of making a
   node is a :ref:`toolset<pyplugWriting-toolsets>`.
5. **Distribution.** Install it on other computers, with its icon and its menu
   (:ref:`pyplugWriting-menus`, :ref:`pyplugWriting-distribute`), make sure it works on render
   farms (:ref:`pyplugWriting-background`), and port PyPlugs written for Natron 2.3 or older
   (:ref:`pyplugWriting-python3`).
6. **Debugging.** Find out why a PyPlug doesn't appear or fails (:ref:`pyplugWriting-debug`),
   and avoid the usual mistakes (:ref:`pyplugWriting-pitfalls`).

.. see pyplugWriting-renderReadBack, once #1478 and #1480 are merged: rendering and reading
   back the result, waitForRenders, undo groups, and what works headless. Link it from step 3.

.. mermaid::

.. _pyplugWriting-file:

The PyPlug file
---------------

A PyPlug is a ``.py`` file in one of the :ref:`plug-in search paths<natronPath>` (or one of their
sub-directories). The file name, without ``.py``, is the name of the Python module: it must be a
valid Python module name, so don't use spaces or dashes in it.

Natron reads every ``.py`` file in the search paths at startup, after running the
:ref:`startup scripts<startupScripts>`. A file is taken as a PyPlug if one of its lines starts with
``# Natron PyPlug`` (or with ``# This file was automatically generated by``, as in exported files,
or with ``def createInstance(`` or ``def getIsToolset(``). Natron then imports the module, by its
file name, and reads these functions:

.. list-table::
   :header-rows: 1
   :widths: 30 15 55

   * - Function
     - Required
     - Returns
   * - ``getLabel()``
     - yes
     - The label shown in the menus, and the default name of new nodes.
   * - ``createInstance(app, group)``
     - yes
     - Nothing. Creates the nodes and parameters inside *group*, the Group node created by Natron
       (see :ref:`below<pyplugWriting-createInstance>`).
   * - ``getPluginID()``
     - no
     - The unique plug-in ID, e.g. ``"org.example.MyBlur"``. Defaults to the label.
   * - ``getVersion()``
     - no
     - The major version, an integer (not a string). Defaults to 1.
   * - ``getGrouping()``
     - no
     - The menu where the PyPlug appears, e.g. ``"Filter/MyStudio"``: menu levels are separated by
       ``/``. Defaults to ``"Other"``. See :ref:`pyplugWriting-menus`.
   * - ``getPluginDescription()``
     - no
     - The description shown by the **?** button of the settings panel. (``getDescription()``
       is accepted too, for old PyPlugs.)
   * - ``getIconPath()``
     - no
     - The icon file, relative to the directory of the script, e.g. ``"MyBlur.png"``. If the file
       doesn't exist, the PyPlug has no icon.
   * - ``getIsToolset()``
     - no
     - ``True`` if the file is a :ref:`toolset<pyplugWriting-toolsets>`. Defaults to ``False``.
       It must return ``True`` or ``False``: other values, even ``1``, are not supported (see
       `#1528 <https://github.com/NatronGitHub/Natron/issues/1528>`_).

If the module can't be imported (for example because of a syntax error), Natron writes
*Was not recognized as a PyPlug* and the Python error to the error log
(:menuselection:`Display --> Show Project Errors Log...`). If ``getLabel()`` or
``createInstance()`` is missing, the file is silently ignored. See also :ref:`debuggingPython`.

.. _pyplugWriting-createInstance:

createInstance(app, group)
--------------------------

Natron calls ``createInstance(app, group)`` each time the user creates the PyPlug node, or a
script calls ``app.createNode(pluginID)``. *app* is the :ref:`application instance<App>` and
*group* is the new, empty Group node. The function creates the nodes inside the group, connects
them, and adds the parameters that the user sees on the group.

A group needs an *Input* node for each input and an *Output* node:

- ``fr.inria.built-in.Input`` creates an input of the group. The label of the Input node
  is the input label shown on the node graph.
- ``fr.inria.built-in.Output`` creates the output of the group.

Create the nodes with ``app.createNode(pluginID, -1, group)``, so that they are created
inside *group* and not in the main node graph.

Here is a complete hand-written PyPlug: a blur whose size is controlled by one parameter of the
group. Save it as ``SimpleBlur.py`` in ``~/.Natron`` (or another search path) and restart Natron::

    # Natron PyPlug

    import NatronEngine

    # Optional hand-written additions, see "The Ext.py file" below
    try:
        from SimpleBlurExt import *
    except ImportError:
        pass

    def getPluginID():
        return "org.example.SimpleBlur"

    def getLabel():
        return "SimpleBlur"

    def getVersion():
        return 1

    def getGrouping():
        return "Filter/Examples"

    def getPluginDescription():
        return "Blurs the input. The amount of blur is set by the Size parameter."

    def createInstance(app, group):
        # The user parameters of the group, on a page of their own
        page = group.createPageParam("controls", "Controls")
        size = group.createDoubleParam("blurSize", "Size")
        size.setMinimum(0.)
        size.setDisplayMaximum(100.)
        size.setDefaultValue(10.)
        page.addParam(size)
        group.refreshUserParamsGUI()

        # The nodes inside the group
        source = app.createNode("fr.inria.built-in.Input", -1, group)
        source.setScriptName("Source")
        source.setLabel("Source")
        blur = app.createNode("net.sf.cimg.CImgBlur", -1, group)
        output = app.createNode("fr.inria.built-in.Output", -1, group)

        blur.connectInput(0, source)
        output.connectInput(0, blur)

        # Drive the blur size (both dimensions) from the group parameter
        blur.getParam("size").setExpression("thisGroup.blurSize.get()", False, 0)
        blur.getParam("size").setExpression("thisGroup.blurSize.get()", False, 1)

        # Let SimpleBlurExt.py, if it exists, add to the group
        if "createInstanceExt" in globals():
            createInstanceExt(app, group)

Then create it from the node menus (:menuselection:`Filter --> Examples --> SimpleBlur`), or with::

    app.createNode("org.example.SimpleBlur")

.. note::

    In expressions inside a PyPlug, refer to the nodes and parameters of the group with the
    ``thisGroup.`` prefix, as above. Without it, the expression looks for a node of the main
    node graph, which doesn't exist in the user's project (see :ref:`paramExpr`).

The PyPlug is **imported** as a module: inside it, only the arguments of ``createInstance``,
the modules it imports, and its own globals are visible. Don't rely on the ``app1`` variables or
on the nodes of the user's project.

.. _pyplugWriting-params:

Parameters of a PyPlug
----------------------

The parameters that the user sees on a PyPlug node are the *user parameters* of its Group: in the
user interface, add them with *Manage user parameters...* (see :ref:`groups`); in a script, create
them with the ``create...Param(name, label)`` functions of the group, put them on a page, and call
:func:`group.refreshUserParamsGUI()<NatronEngine.UserParamHolder.refreshUserParamsGUI>` once they are all
created. Set the label, the animation, the layout (``setAddNewLine()``), and the type of string,
group and path parameters (``setType()``, ``setAsTab()``, ``setAsMultiPathTable()``) before that
call: they can't be changed afterwards. The help, the range, the visibility and the value can change at any
time.

A group parameter can drive the nodes inside the group in three ways:

- an **expression** on the inner parameter, e.g. ``thisGroup.blurSize.get()`` as in the example
  above. The expression can compute anything (``thisGroup.blurSize.get() * 2``), and it is
  evaluated at each frame, so it follows the animation of the group parameter;
- an **alias**, made with the *Pick* button of the *Manage user parameters* dialog, or with
  :func:`setAsAlias()<NatronEngine.Param.setAsAlias>`: the group parameter *is* the inner
  parameter, with its menu, range and animation. Use it for menus that change with the input,
  such as the layer or channel menus;
- a **link**, made with :func:`slaveTo()<NatronEngine.Param.slaveTo>`: one dimension of the inner
  parameter copies one dimension of the group parameter.

Use an expression or a link for a value that depends on other values, and a
:ref:`callback<callbacks>` for an action: a button, showing or hiding parameters, or adding nodes.
Expressions are evaluated where they are needed, also during the render, while a callback is only
called when a parameter changes, in the main thread, and not when only the current frame changes
(see :ref:`paramExpr` and :ref:`callbacks`).

.. _pyplugWriting-ext:

Exported PyPlugs and the Ext.py file
------------------------------------

The **Export as PyPlug** button, in the *Node* tab of a Group's settings panel, writes the
Group as a PyPlug (see :ref:`groups-export` for the dialog). The *Label* is also the file name,
``<Label>.py``, so Natron makes it a valid Python module name: spaces become underscores, the
other characters that a module name can't contain are removed, a leading digit gets a ``p``
prefix, and ``from`` and ``lambda`` become ``pFrom`` and ``pLambda``. ``getLabel()`` returns the
label after this change, and the menus show it.

The exported file has this layout:

- a header: ``# -*- coding: utf-8 -*-``, ``# DO NOT EDIT THIS FILE``, the ``# Natron PyPlug``
  line, the version of the exporter, the name of the Ext file, and a link to this section of the
  documentation of the Natron version that wrote the file (for Natron 2.6,
  ``https://natron.readthedocs.io/en/rb-2.6/devel/pyplug-writing.html#pyplugwriting-ext``);
- ``import NatronEngine``, and the import of the Ext file (see below);
- the functions ``getPluginID()``, ``getLabel()``, ``getVersion()``, ``getGrouping()``, and
  ``getIconPath()`` and ``getPluginDescription()`` if you gave an icon and a description;
- ``createInstance(app, group)``, which creates the user parameters of the group, then each node
  with its parameters, then the connections and the expressions. Viewer nodes are not exported.

Exporting the Group again overwrites the file, so don't edit it.
Put hand-written code in a second file, ``<Label>Ext.py``, in the same directory. The exported
script imports everything from it (``from <Label>Ext import *``) if it exists, and its
``createInstance()`` ends by calling ``createInstanceExt(app, group)`` if the Ext module defines it.
Use it to set callbacks, or to change the group after it is built. A hand-written PyPlug only gets
these two hooks if it has the same lines, as the ``SimpleBlur.py`` example above does.

This Ext file adds a button that puts the *Size* parameter of ``SimpleBlur`` back to its default
value (with an exported PyPlug, use its parameter and page names instead of ``blurSize`` and
``controls``)::

    # This is SimpleBlurExt.py, next to SimpleBlur.py

    def paramChanged(thisParam, thisNode, thisGroup, app, userEdited):
        # Called for every parameter of the group: check which one changed
        if thisParam.getScriptName() == "resetSize":
            thisNode.getParam("blurSize").restoreDefaultValue()

    def createInstanceExt(app, group):
        reset = group.createButtonParam("resetSize", "Reset Size")
        reset.setHelp("Puts the Size parameter back to its default value.")
        group.getParam("controls").addParam(reset)
        group.refreshUserParamsGUI()
        group.onParamChanged.set("SimpleBlur.paramChanged")

Pressing a button calls the *param changed* callback of its node, with the button as
``thisParam`` (unless the node is disabled). Since the callback is called for every parameter, test
the script name first.

A callback defined in a PyPlug is registered with the **module name of the PyPlug** as prefix
(``SimpleBlur.paramChanged``), even when it is defined in the Ext file, because the PyPlug
module imports the content of the Ext module. See :ref:`callbacks` for the signatures.

.. _pyplugWriting-versions:

Plug-in IDs and versions
------------------------

Choose a unique plug-in ID, in reverse domain notation (``org.mystudio.MyEffect``), and keep it
stable: projects store the plug-in ID and the version of each node.

When you change a PyPlug in a way that changes the result of existing projects, increase the
version returned by ``getVersion()`` and keep the old file too. Several versions of the same
plug-in ID can be installed side by side: new nodes use the highest version, and
``app.createNode(pluginID, majorVersion)`` picks a given one. If two files have the same plug-in
ID and version, Natron uses the first one found in the search paths. The two versions must be in
files with different names, e.g. ``MyEffect.py`` and ``MyEffect2.py``: Natron loads only one file
of each name (see :ref:`pyplugWriting-pitfalls`).

.. _pyplugWriting-update:

Changing an installed PyPlug
----------------------------

A PyPlug node is locked: the user can change the values of its parameters, but not the nodes
inside it nor its list of parameters. Its node graph shows a lock at the top right. To edit it:

1. create the PyPlug node, and make it a regular Group: click **Convert to Group** in its *Node*
   tab, or click the lock in its node graph. *Manage user parameters...* also offers to convert it;
2. make the changes;
3. click **Export as PyPlug**. When the Group comes from a PyPlug, the dialog starts with the
   values of that PyPlug (ID, label, grouping, icon, description and directory), so OK
   overwrites the same file. The *Version* always starts at 1 (see
   `#1527 <https://github.com/NatronGitHub/Natron/issues/1527>`_): enter the version of the
   PyPlug again, plus one if the change modifies the result of existing projects (see
   :ref:`pyplugWriting-versions`). Otherwise a version 2 PyPlug is overwritten as version 1;
4. restart Natron: PyPlugs are read only at startup, and so are their Ext files.

A PyPlug can hide the lock of its node graph with
:func:`group.setSubGraphEditable(False)<NatronEngine.Effect.setSubGraphEditable>`, e.g. in
``createInstanceExt()``. This only hides the lock: **Convert to Group** and *Manage user
parameters...* still make the node editable.

A project stores the whole content of each PyPlug node (its nodes, parameters and connections),
with the path and the version of the PyPlug file. A project therefore opens on a computer where the
PyPlug isn't installed: its nodes are loaded as Groups, and the callbacks defined in the PyPlug
don't run.

.. note::

    With the *Load PyPlugs in projects from .py if possible* preference (*Python* tab) checked
    (the default), Natron runs the installed PyPlug file again for each PyPlug node of a project,
    and asks whether to use it when its version differs from the one saved in the project. When it
    is unchecked, or when the PyPlug file isn't found, Natron loads each PyPlug node from the
    content saved in the project. From Natron 2.2 to the 2.6 betas, the preference had the opposite
    effect (`#1646 <https://github.com/NatronGitHub/Natron/issues/1646>`_).

.. _pyplugWriting-menus:

Menus and icons
---------------

``getGrouping()`` returns the menu path of the PyPlug, with ``/`` between the levels, e.g.
``"Filter/MyStudio"``. The first level is a button of the toolbar on the left:

- if it is the name of a Natron category (``Image``, ``Draw``, ``Time``, ``Channel``, ``Color``,
  ``Filter``, ``Keyer``, ``Merge``, ``Transform``, ``3D``, ``Deep``, ``Views``, ``ToolSets``,
  ``Other``, ``Misc``), the PyPlug goes into that menu, which keeps its icon;
- any other name adds a new toolbar button, with a generic icon. A PyPlug can't set the icon of a
  toolbar button, only its own icon.

Don't end the grouping with ``/``: that adds a sub-menu without a name.

The icon of the PyPlug, returned by ``getIconPath()``, is shown in the menus. Use a square PNG
file next to the ``.py`` file: Natron scales it to the size of the menus.

.. _pyplugWriting-toolsets:

Toolsets
--------

A toolset is a PyPlug whose ``getIsToolset()`` returns ``True``. Natron doesn't create a Group
node for it: it calls ``createInstance(app, group)`` with ``group`` set to an empty string
(``""``), and the function adds nodes to the current node graph, for example a predefined chain
of nodes. The *Split and Join* entry of the *Views* menu is a toolset bundled with Natron.
A minimal toolset::

    # Natron PyPlug

    def getPluginID():
        return "org.example.ReadAndBlur"

    def getLabel():
        return "Read and blur"

    def getIsToolset():
        return True

    def createInstance(app, group):
        # group is "" for a toolset: create the nodes in the project
        reader = app.createNode("fr.inria.built-in.Read")
        blur = app.createNode("net.sf.cimg.CImgBlur")
        blur.connectInput(0, reader)

``app.createNode()`` returns ``None`` for a toolset, since no node stands for it.

.. _pyplugWriting-background:

PyPlugs in background mode
--------------------------

Render farms run NatronRenderer, where the NatronGui module doesn't exist. In background mode,
Natron **skips** every PyPlug file with a line that starts with ``import NatronGui`` or
``from NatronGui import``: such a PyPlug can't be created there, and the nodes of a project that
uses it are loaded as plain Groups, from the content saved in the project, without the callbacks
of the PyPlug. Keep GUI code
(dialogs, panels) out of the PyPlug: put it in ``initGui.py``, or in a separate module that the
PyPlug only imports inside ``if not NatronEngine.natron.isBackground():``.

In background mode, :meth:`app.waitForRenders()<NatronEngine.App.waitForRenders>` waits for the render
threads, :meth:`app.undoGroup()<NatronEngine.App.undoGroup>` records nothing (the edits are made, as
usual), and :meth:`app.undo()<NatronEngine.App.undo>`, :meth:`redo()<NatronEngine.App.redo>`,
:meth:`canUndo()<NatronEngine.App.canUndo>` and :meth:`getUndoHistory()<NatronEngine.App.getUndoHistory>`
do nothing (there is no undo stack). The viewer functions (``app.getViewer()``) only exist in the user
interface.

.. _pyplugWriting-renderReadBack:

Rendering, reading back the result, undo
----------------------------------------

A PyPlug button that renders and reads the result back (e.g. to "bake" a value into a parameter) can
ask the viewer for the image, once the render is displayed. :meth:`app.waitForRenders()<NatronEngine.App.waitForRenders>`
returns when no render runs any more and its result is shown, and
:meth:`PyViewer.getPixel()<NatronGui.PyViewer.getPixel>` returns the linear colour of the image (the value
of the colour picker, before the display LUT)::

    def onBakeButton(thisNode, app):
        # the viewer functions only exist in the user interface
        if NatronEngine.natron.isBackground():
            return
        viewer = app.getViewer("Viewer1")
        viewer.fit()  # as the F key
        viewer.renderCurrentFrame()
        if not app.waitForRenders(30):
            return  # timeout
        rod = thisNode.getRegionOfDefinition(app.timelineGetTime(), 0)
        c = viewer.getPixel((rod.left() + rod.right()) / 2, (rod.bottom() + rod.top()) / 2)
        thisNode.getParam("measured").set(c.r, c.g, c.b, c.a)

:meth:`PyViewer.getImage()<NatronGui.PyViewer.getImage>` returns the whole image (or a region) as
32-bit floats, e.g. for a custom scope: ``bounds, data = viewer.getImage(); pixels = array.array('f', data)``.
:meth:`PyViewer.getZoom()<NatronGui.PyViewer.getZoom>`, :meth:`setZoom()<NatronGui.PyViewer.setZoom>`,
:meth:`getCenter()<NatronGui.PyViewer.getCenter>` and :meth:`setCenter()<NatronGui.PyViewer.setCenter>`
set up the view, e.g. for a review tool.

Edits made from Python are not undoable, unless they are made in an undo group: then they are one
undo step, which *Edit > Undo* in the node graph (or :meth:`app.undo()<NatronEngine.App.undo>`)
undoes at once. A button callback that builds a few nodes makes them one step::

    def onBuildButton(thisNode, app):
        with app.undoGroup("Build blur"):
            blur = app.createNode("net.sf.cimg.CImgBlur")
            blur.connectInput(0, thisNode)
            blur.getParam("size").set(10, 10)

The group records the parameter changes, and the nodes created, deleted and connected: see
:meth:`app.undoGroup()<NatronEngine.App.undoGroup>` for what it does not record.

:meth:`app.undo()<NatronEngine.App.undo>`, :meth:`app.redo()<NatronEngine.App.redo>` and
:meth:`app.getUndoHistory()<NatronEngine.App.getUndoHistory>` work on the undo stack of the node graph
(node creation, deletion, connections, undo groups). These functions must be called from the main thread: from a
button or param changed callback, not from a render callback such as *afterFrameRender*.

.. _pyplugWriting-distribute:

Distributing PyPlugs
--------------------

A PyPlug is a directory with the ``.py`` file, its optional ``Ext.py`` file and its icon. To
install it, copy the directory into a search path: ``~/.Natron`` for one user, the system
location for all the users of a computer, or a shared directory listed in ``NATRON_PLUGIN_PATH``
or in the "PyPlugs search path" preference (see :ref:`natronPath`). PyPlugs are registered at
startup, so restart Natron after installing one.

Since all the directories of the search paths are added to the Python path, a PyPlug can import
Python modules installed next to it.

The search paths are searched recursively, so a collection of PyPlugs can be one directory with a
sub-directory per PyPlug, or per category, as in the community
`natron-plugins <https://github.com/NatronGitHub/natron-plugins>`_ repository. Add only the top
directory to the search path. When you export into a sub-directory of a search path, the export
dialog offers to add that sub-directory too: you can answer *No*, Natron finds it anyway.

Before you share a PyPlug:

- give it a description (``getPluginDescription()``), shown by the **?** button of its settings
  panel, and a help text on each parameter (``setHelp()``);
- prefix the file names, e.g. ``mystudio_Glow.py``, so that they don't clash with other PyPlugs or
  with Python modules (see :ref:`pyplugWriting-pitfalls`);
- if the PyPlug uses OpenFX plug-ins that are not bundled with Natron, say so: on a computer where
  one of them is missing, creating the PyPlug fails.

.. _pyplugWriting-python3:

Python 3, PySide2 and PySide6
-----------------------------

Natron 2.6 embeds Python 3, with PySide2 in its Qt 5 builds and PySide6 in its Qt 6 builds
(see :ref:`pythonEnvironment`). PyPlugs written for Natron 2.3 or older used Python 2 and PySide,
and often need these changes:

- ``print x`` becomes ``print(x)``, ``except Exception, e:`` becomes ``except Exception as e:``,
  and ``unicode``, ``basestring`` and ``xrange`` no longer exist. Until it is fixed, such a file
  can't be imported, and Natron writes *Was not recognized as a PyPlug* and the Python error to the
  error log;
- ``/`` between integers gives a float: use ``//`` for an integer division, e.g. for a frame
  number;
- replace ``from PySide import QtGui`` (or ``PySide2``) with
  ``from qtpy import QtCore, QtGui, QtWidgets``, which works with both PySide2 and PySide6. The
  widgets (``QDialog``, ``QPushButton``...) are in ``QtWidgets``, not in ``QtGui``.

Keep Qt code out of the PyPlug file itself, as explained in :ref:`pyplugWriting-background`.

.. _pyplugWriting-debug:

Debugging a PyPlug
------------------

When a PyPlug doesn't appear in the menus, check the error log
(:menuselection:`Display --> Show Project Errors Log...`) and the list in :ref:`debuggingPython`.
NatronRenderer is a quick way to test the PyPlug without starting the user interface: this script
lists the plug-in IDs that contain a word, and creates the PyPlug::

    # testMyEffect.py, run with: NatronRenderer -t testMyEffect.py < /dev/null
    from NatronEngine import natron
    print(natron.getPluginIDs("mystudio"))
    node = natron.getInstance(0).createNode("org.mystudio.MyEffect")
    print(node, [n.getScriptName() for n in node.getChildren()])

``-t`` opens a Python prompt once the script has run: ``< /dev/null`` ends it at once (on Windows,
end the script with ``quit()`` instead), or leave it out to inspect the nodes at the prompt.

Errors in ``createInstance()`` are printed in the terminal, or shown in a dialog in the user
interface. Errors in callbacks are printed in the Script Editor. Set ``NATRON_PLUGIN_PATH`` to the
directory of the PyPlug to test it without installing it (see :ref:`natronPath`).

.. _pyplugWriting-pitfalls:

Pitfalls
--------

These mistakes are the most frequent ones, and most of them fail without any message.

**File names are Python module names, shared by all the search paths.**
    Natron imports each PyPlug by its file name. If two PyPlugs in different directories have the
    same file name, only the first one found is loaded. A file named like a Python module that
    already exists (``colorsys.py``, ``string.py``...) is ignored. Prefix your file names.

**The values returned by the functions must have the right type.**
    ``getVersion()`` returns an integer, and ``getIsToolset()`` must return ``True`` or ``False``:
    other values, even ``1``, are not supported
    (`#1528 <https://github.com/NatronGitHub/Natron/issues/1528>`_).

**Callbacks need the module name, and a public name.**
    Register a callback as ``MyPyPlug.myCallback``, with the arguments named as in
    :ref:`callbacks`. ``from MyPyPlugExt import *`` doesn't import the names that start with
    ``_``, so don't use such names for the functions of the Ext file.

**Use the app that Natron gives you.**
    In a PyPlug or a callback, use the ``app`` argument: ``app1`` is only the first project, and
    the user may have opened several. In a script run by Natron or NatronRenderer, never assign to
    the global variables ``app`` or ``app1``, e.g. ``app = natron.getInstance(0)``: Natron uses them
    to find the nodes that a script creates, and in NatronRenderer the PyPlug nodes can then no
    longer be created (`#1525 <https://github.com/NatronGitHub/Natron/issues/1525>`_). Use another
    name.

**Expressions inside a PyPlug start with thisGroup.**
    See the note in :ref:`pyplugWriting-createInstance`.

**Menus that depend on the input are empty when the PyPlug is created.**
    The exported script sets each menu by the name of its entry. A layer or channel menu, e.g. of a
    Shuffle node, only has the layers of the input, and the PyPlug is created before its input is
    connected: the value can't be set, and the menu goes back to its default. Make such a menu an
    alias on the group (*Pick*, see :ref:`pyplugWriting-params`), so that the user chooses the
    layer once the input is connected.

**Some settings are not exported.**
    The *Use Point Interact* option of a 2D parameter is not written to the exported file
    (`#1526 <https://github.com/NatronGitHub/Natron/issues/1526>`_), so the exported PyPlug has no
    point to drag in the viewer for that parameter.

**A Group needs an Output node to be exported.**
    *Export as PyPlug* refuses a Group without an Output node, even if its last node is a Write
    node. Connect an Output node to the node before the Write node.

**Callbacks are not called for each frame.**
    A callback runs when a parameter changes, not when the animation of a parameter changes its
    value at another frame. For a value that changes with the frame, use an expression. Frames are
    rendered in parallel, in any order: don't keep anything from one frame to the next in Python
    variables.

**A PyPlug doesn't process pixels in Python.**
    A PyPlug only builds a graph of existing nodes. For an effect that no node does, use, inside
    the PyPlug, a node that runs code written by you, such as the G'MIC, Shadertoy or SeExpr nodes.

**A PyPlug doesn't see the variables of the command line.**
    Variables set with ``NatronRenderer -c "myValue=2" ...`` are globals of the ``__main__``
    module, not of the PyPlug module. Read them with ``import __main__`` and
    ``getattr(__main__, "myValue", None)``, or pass the data in environment variables
    (``os.environ``).

**Changes are seen only after a restart.**
    Natron reads the PyPlugs and their Ext files at startup. Existing projects keep the PyPlug
    nodes that they saved: see :ref:`pyplugWriting-update`.

**NatronGui can't be imported by the PyPlug file.**
    See :ref:`pyplugWriting-background`.
